## Findings, ranked by impact

### 1. The sequencer has no cursor: every block re-walks every note of the song, and the harness that says the engine is cheap loads one note per channel — HIGH as this grows

`Sequencer::schedule` runs once per span per block (`render.rs:5636`, up to
`MAX_BLOCK_SPANS = 8`), and each run is a walk of the whole store:

- Pattern mode (`sequencer.rs:844-880`): for every active channel, `for note
  in channel.notes().iter()` — every note, filtered only by `start_tick <
  pattern_ticks` — and per note two calls to `schedule_note_edge`
  (`:959-1000`), each doing an `f64` divide, a `ceil`, and a wrap loop, to
  decide whether that edge falls in this block. A block that contains no
  edge at all does the same work as one that contains ten.
- Song mode (`sequencer.rs:888-957`): `for placement in &self.playlist`
  (up to `MAX_PLAYLIST_PLACEMENTS = 512`) × every active channel × every
  note of that pattern, per block, with no test of whether the placement
  covers the block before entering the note loop. The playlist is sorted
  (`sequencer.rs:139,209`) by `PatternPlacement`'s derived `Ord`, which is
  `(pattern, start_tick)` (`playlist.rs:37-42`), so the sort cannot be used
  to prune by time even if someone tried.
- `automation_lane_at` (`sequencer.rs:554-598`) is the same shape for
  lanes: `(0..active_channels).find_map(..)` per destination per block, and
  a full playlist walk in Song mode. `has_automation_at` (`:477-501`) and
  `song_length_ticks` (`:150-162`, another playlist walk, called per block
  in Song mode) exist to hoist one of those walks; the doc comment on
  `has_automation_at` describes the cost it dodges as "descriptor count
  times channel count, squared into the channel count again".

The notes are already sorted by `(start_tick, id)` — `upsert_note` keeps
them so with a binary search (`pattern.rs:145`) — and nothing reads them as
sorted. A `partition_point` on the block's tick window (two ranges when the
pattern wraps, widened by the largest swing offset, `swing_offset_ticks`
`:1020-1027`) turns the on-edge walk into O(log n + k). Note-offs are not
sorted by end tick; a second index per `ChannelPattern`, `(end_tick, index)`,
maintained at the same edit sites, gives them the same shape. The playlist
needs one sort by `start_tick` and one `partition_point` per block.

Why this outranks everything else: it is O(song) per block, at 750 blocks
per second at a 64-frame period, on the one thread that cannot be late, and
every ceiling the product has committed to raises it — `pattern-bank-floor`'s
README already says a longer part means a longer pattern, not a clip. And
the number that currently says "the engine is not a problem" (13-16% of a
quantum on the heaviest document, `pattern-bank-floor/00-status.md`) comes
from `block_cost.rs`, whose projects hold **one note per channel**
(`loaded_project`, `block_cost.rs:48-57`) and whose Song-mode case does not
exist. It measures synthesis. It has never measured scheduling. Plan A.

### 2. Coefficients are recomputed from parameters every sample, in every voice, for values that change once a block — MEDIUM, systemic

The one filter primitive, `Svf::tick` (`crates/mooloop-dsp/src/filter.rs:89-110`),
takes `cutoff_hz` and `sample_rate` and computes `tan()`, a divide, and
three products per call, per stage — and it is called per sample from
fifteen files (86 sites). Around it, each generator derives the cutoff it
passes with more transcendentals per sample per voice:

- sampler (`sampler.rs:1007-1012`): `hz_from_normalized` (`scale.rs:11`,
  a `powf`), a second `powf` for the envelope, then a hand-copied SVF with
  its own `tan` and divide; `apply_drive` (`filter.rs:254-263`) adds two
  `tanh` of which one, the compensation, is a constant of `drive`;
- mono (`monosynth.rs:273-275`), poly (`polysynth.rs:481-483`), ML-M1
  (`mlm1.rs:525`) and ML-P8 (`mlp8.rs:2435`): `hz_from_normalized` per
  sample from a `Smoothed` cutoff (`voice.cutoff.advance()`) that has
  settled to a constant for the whole life of most notes;
- the phaser (`effects/modulation.rs:187-228`): per sample, per stage (up
  to `MAX_PHASER_STAGES = 12`), per channel, two `powf` in `phaser_hz` and
  one `tan` in `allpass_coefficient` — up to 72 transcendental calls per
  sample for one effect instance — where `28.0f32.powf(color)` (`:210`) is
  the same number for all 24 of those calls and for the whole block;
- the compressor's makeup (`effects/dynamics.rs:285`): `db_to_linear` per
  sample of a value automated approximately never;
- the sine oscillator (`osc.rs:221`): `(phase * TAU).sin()` per sample,
  which the module's own header calls naive.

The tree already knows the right shape and uses it in two places: delay
(`effects/delay.rs:149-153,201-202`) and reverb (`effects/reverb.rs:448-461`)
derive the coefficient in `apply_param` and smooth *that*. The rest smooth
the parameter and re-derive the coefficient per sample, which is the
expensive order. The justification written at `filter.rs:20-22,50-51` — an
envelope sweeps cutoff every sample — is true and does not need per-sample
`tan`: the standard answer is to compute the coefficient set at each control
tick (32 frames, the rate the engine already resolves modulation at) and
linearly interpolate `g, a1, a2, a3` across the tick. The SVF is stable
under interpolated coefficients; that is what "topology-preserving" buys.

This is not a crash and not measured as a problem today. It is the reason
the per-voice cost is what it is, and it is where the headroom for a
plugin's worth of DSP per channel will come from. Plan B.

### 3. Automation reaches a device as a stream of step events in the note list, while the engine already has the right representation next to it — MEDIUM (deepens 09-21 finding 5)

A driven parameter is resolved once per control tick and pushed as an
`Event::ParamValue` into the channel's `EventList` (`render.rs:1360-1387`
for effects, `:5917-5936` for sources, `:5967-5990` for routes), by
`push_ordered` (`event.rs:117-131`, an insertion into a 256-slot array,
O(n) per push). The device then splits its block at every event
(`effects/mod.rs:75-91`; the generators have the same loop), so one
automated parameter renders the block in 32-frame pieces, and each piece
re-enters `apply_param`, which for the EQ rebuilds all 19 biquads on both
channels (`effects/eq.rs:79-89`) and for plate and reverb the whole comb
bank (`plate.rs:294-320`, `reverb.rs:427-462`) — every 32 frames.

The capacity is the notes' capacity: `MAX_EVENTS = 256` (`event.rs:70`),
whose comment reasons about a bar of 32nds. At `MAX_BLOCK_SIZE = 8192`
(`bus.rs:15`) one destination emits 256 events and fills the list alone; a
second is silently dropped (`let _ =`, `render.rs:5931,5983`). At 1024
frames, eight destinations do the same. Nothing counts it.

Beside this path the engine keeps two per-tick tables for exactly this
information: `ControlOutputs` (`render.rs:694`, modulator values per tick)
and `StripSegments` (`render.rs:1972-1976`, gain and pan per tick for the
fader). The fader is driven by a table; a filter cutoff is driven by a
sorted list of events that decode into the same table one step at a time.
One representation — a per-destination `[f32; ticks]` curve from a small
pool, handed to the node as a curve — removes the cap, the sort, the
sub-block re-entry and the per-tick `apply_param` cost at once. Events
with sample offsets stay for what they are for (notes, and the plugin
boundary, where CLAP wants them); a curve becomes events only there.
Plan C.
