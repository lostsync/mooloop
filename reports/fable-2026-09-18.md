# Whole-system review, 2026-09-18

Scope: seams (two owners, duplicate abstractions, UI/engine drift), real-time
safety of the audio callback, and architecture fit for automation, recording,
plugin hosting and instrument tracks. Read against `main` at `f2f2dfd`, one
day after `reports/fable-2026-09-17.md`, whose five plans all landed.

Method: six parallel Sonnet investigators, each briefed to skip anything in
`docs/LOOSE_ENDS.md` or yesterday's report: (1) the 24 commits since
`1009be4`, for RT safety and new two-owner state; (2) a systematic RT sweep
from the JACK/Core Audio callbacks down; (3) engine commands that
`install_project` does not restore, and session mirrors; (4) `dupe-audit` and
twin types; (5) the four live plans' assumptions against the code; (6) the
UI/session seam. Every kept finding was re-read at the cited lines by the
author. Nothing in the source was changed.

## Findings, ranked by impact

Lower than yesterday, and that is the result: the five plans landed, and the
class they belonged to (state an install rebuilds and a command sets) is now
guarded at `InputState`, `SharedCells` and `survives_project_load`, all three
re-read and intact. What is left is smaller.

### 1. The toolbar's Add Channel is the one channel edit undo cannot see — LOW/MEDIUM

`on_add_channel_clicked` (`crates/mooloop-ui/src/lib.rs:7998-8039`) calls
`Session::add_channel` (`crates/mooloop-session/src/rack.rs:139-154`) and
sends `PendingEngineMessage::AddChannel` (`crates/mooloop-session/src/engine.rs:688-693`),
the incremental `StructuralCommand::AddChannel`. It never calls
`record_project_history` (`lib.rs:1398`); the paste/clone path
`queue_channel_insert` (`lib.rs:1419-1458`) does. The document goes dirty
(`engine.rs:692`) and the history does not move.

What a user sees: click `+`, press Ctrl+Z, and either nothing happens or the
previous recorded edit's snapshot is installed and the new channel vanishes
with no redo, the mechanism `LOOSE_ENDS.md` "An undo of one edit silently
destroys every unrecorded edit" describes. That entry's list of unrecorded
surfaces does not include channel add, and `docs/CURRENT.md:1609` says
"channel structure" feeds the undo stack. It does, except this verb.

The incremental path is the right one: it is the only structural edit that
does not stop the song. It just needs the snapshot pair around it. Plan C.

### 2. New Song installs without the stale-queue filter Open Song has — LOW

`survives_project_load` (`crates/mooloop-session/src/engine.rs:144-162`) exists
because a routing table or spectrum subscription queued before a load is
indexed by the outgoing project and, applied afterwards, overwrites what the
install carried for the incoming one. The Open path drains and filters
`pending_rx` before `install_project_in_ui` (`crates/mooloop-ui/src/lib.rs:12896-12910`).
The New Song path calls `install_project_in_ui` with no filter
(`lib.rs:12620-12629`).

Reachability is one pump tick: the pump drains `document_rx` (`lib.rs:12611`)
*before* `pending_rx` (`lib.rs:13102`) in the same tick, so anything a
callback queued since the previous tick is applied after the install rather
than before it. `document-busy` disables only the File menu
(`ui/main.slint:2490`), so the MIDI-input picker and every knob stay live
while the "Discard unsaved song changes?" thread is up (`lib.rs:5466-5482`).
A user who changes a channel's MIDI input and confirms New Song within the
same 8 ms gets the old project's routing over the starter kit's. Rare, but
the two install paths are the same operation with different guards, which
is how the routing bug of 2026-09-17 arrived. Fix: move the drain-and-filter
into `install_project_in_ui` or a helper both call. Plan B.

### 3. The oscillator tuning range is spelled four times and nothing reads two of them against each other — LOW

`-48..48` semitones and `-100..100` cents live in two independent Rust tables
and two independent Slint literals:

- `crates/mooloop-core/src/generator.rs:456-457,464-465` (`osc_descriptors`,
  shared by mono/poly/MLM1);
- `crates/mooloop-core/src/mlp8.rs:1235-1236` (MLP8's own `osc_descriptors`);
- `crates/mooloop-ui/ui/device-oscillator.slint:79` (`minimum: -48; maximum: 48`,
  the component mono/poly/MLM1 instantiate);
- `crates/mooloop-ui/ui/mlp8-device.slint:482` (`P8Knob`, inline).

No test reads any pair. `slint_face_agreement.rs` never `include_str!`s
`device-oscillator.slint` (lines 28-50; `git log -S` finds it never did),
and for `mlp8-device.slint` it checks only the six envelope stages in
`ENVELOPES` (lines 234-256) and walks `ParameterKnob` blocks, not `P8Knob`.
`scripts/dupe-audit unchecked-face` cannot report it either: it keys on
`default-value:` *literals* (`scripts/dupe-audit:304`), and the oscillator
knob's default is `root.param-defaults[...]`, so a face whose min/max are
literals and whose default is not is invisible to the check.

`docs/LOOSE_ENDS.md:1168` says the test's list "grew to take
`device-oscillator`". It did not. The doc records coverage the tree does not
have — the shape `FOCUS.md` calls "a claim the source no longer supported".

Why it matters: the descriptor comment at `generator.rs:453-455` says the
range must match the knob's travel or a full-depth modulation route sweeps
less than the control offers. That is exactly the drift nothing would notice.
Fix S: Plan A below.

### Real-time safety: swept and clean

The second investigator walked every grep lead (`Mutex`, `lock`, `log`,
`format!`, `Vec::new`, `push`, `Box::new`, `collect`, `assert!`, `unwrap`,
`drop`) from both driver callbacks through `Executor::process`

`taps.rs`, `aux_in.rs`, `analysis.rs`, every ring constructor in

resolved to pre-sized storage (capacity set in `RenderState::new`,
`render.rs:2998-3031`, or at device construction) or to a control/notification
thread. The author separately checked that every `channel`/`bus`/`pattern`
index arriving in an `EngineCommand` goes through `get_mut`/`< active`
(`render.rs:4188-4222`, `sequencer.rs:74-97`) rather than a bare index, and
that the executor's MIDI decode is bounded by `MAX_MIDI_PER_BLOCK`
(`executor.rs:242-251`).

Yesterday's three RT findings are confirmed landed: the sampler retires both
the voice sample and its channel snapshot (`sampler.rs:390-433,723-744,839-853`)
and the executor drains that ring every block (`executor.rs:283-292`);
MLP8's chorus resets in place (`mlp8.rs:951-967`); `RenderState::reclaim` is
pre-sized (`render.rs:3035`). The Core Audio `try_lock` (finding 6 yesterday)
is unchanged and remains the one lock on the thread.

**Zero new RT hazards.** This is a reading, not a measurement; the locks half
of the contract is still measured by nothing.

## Architecture

What follows is checked against the code; the plans' own claims that were
verified true are not repeated.

**`InputState` is a hand-maintained list, and two members are still missing.**
A project install replaces the whole `RenderState`
(`crates/mooloop-engine/src/executor.rs:226`), and what crosses the swap is
nine `SharedCells` (`lib.rs:551-561`) plus `InputState { record_armed,
midi_routing }` (`lib.rs:574-586`), whose doc comment says record arm was
lost this way until 2026-09-17. Two more pieces of performance state are
built fresh at `RenderState::new` and carried by nothing: `held_keys`
(`render.rs:2911,3043`) and the in-flight MIDI capture `recording:
[None; 128]` (`render.rs:2919,3045`). Today that costs a note-off (the old
voices are gone with the old renderer anyway, under "every structural edit
stops the song") and a note-on captured but not yet closed. It matters for
what comes next: `channel-identity/04-keep-the-transport.md` carries the
transport across an edit and names neither field, and
`audio-recording/03-capture.md` puts a capture ring on the audio thread
without saying what an install mid-take does to it. Every plan that adds
renderer-resident state will either add an `InputState` field by hand, the
mechanism that has needed patching three times this month, or land after
`channel-identity/05` makes strips survive. The cheaper order is: `05` before
`audio-recording/03`, not only before `plugin-hosting/06` as now planned.

**Note delivery to a source is a closed match, not a trait call.**
`ChannelStrip::process` (`render.rs:2496-2526`) matches `active_source` over
eight `DeviceKind`s and calls a different, non-uniform method per arm
(`process`, `process_publishing`, `process_from`). `source_node()` exposes
`&dyn AudioNode` only for the rest contract. `plugin-hosting/09` names the
right sites but the same closed shape recurs in `publish_outlets`
(`render.rs:2536+`) and in `mooloop-core`'s per-generator state accessors
(`project.rs:500-514`). A boxed instrument source has to unify the arm
signatures first; that is a refactor worth doing on the eight native sources
before the ninth is foreign.

**Latency is a per-kind constant.** `EffectKind::latency_frames`
(`crates/mooloop-core/src/effect.rs:62-84`) is a static match; nothing asks
a live node. A plugin's latency is known only after activation and can
change. `plugin-hosting/00-status.md` blocker 3 already says so; what it
does not say is that `AudioTapBank` is rebuilt on every install
(`render.rs:3379`), so the compensation plan and the tap bank will both need
the identity work before a plugin's latency can change without a rebuild.

**Recording has no input yet, and the driver seam is the cheap place.**
JACK registers two outputs and one MIDI in (`jack_driver.rs:204-219`);
Core Audio builds an output stream only; `Executor::process` takes no input
buffer (`executor.rs:131-136`). `audio-recording/01` knows this. The one
thing to decide before step 01 is written twice: the input arrives through
the executor's signature, not through a driver-specific side channel, so the
Core Audio driver gets it in the same commit as JACK.

**MIDI control and the input menu do not collide.** `ChannelMidiInput::picker_rows`
(`crates/mooloop-core/src/midi.rs:266-296`) is the list `audio-recording/02`
extends, and the four install-time bugs `midi-control/00-status.md:27-56`
records are the `InputState` shape above, not a menu conflict.
