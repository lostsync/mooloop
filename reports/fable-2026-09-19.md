# Whole-system review, 2026-09-19

Scope: seams (two owners, duplicate abstractions, UI/engine drift), real-time
safety of the audio callback, and architecture fit for automation, recording,
plugin hosting and instrument tracks. Read against `main` at `e19fb80`, one
day after `reports/fable-2026-09-18.md`.

Method: five parallel Sonnet investigators and one Haiku, each briefed to skip
anything in `docs/LOOSE_ENDS.md` or the two previous reports: (1) the
incremental-install carry-over path for RT safety; (2) a systematic RT sweep
from the driver callbacks down; (3) two-owner state, channel identity, undo
and dirty coverage of the new verbs; (4) `dupe-audit`; (5) the live plans'
assumptions against the code; (6) the UI/engine seam. Every kept finding was
re-read at the cited lines by the author. Nothing in the source was changed.

## Findings, ranked by impact

### 1. Every structural edit frees four `Vec`s on the audio thread, and the test that says otherwise never measures the path — MEDIUM

`PreparedProject` (`crates/mooloop-engine/src/lib.rs:395-415`) carries the
incoming renderer as a `Box` and the carry plan as four `Vec<(u8, u8)>`
(`CarryPlan`, `lib.rs:426-439`), built by `collect()` on the control thread
(`lib.rs:709-718`) for **every** install that has a live project
(`install_project`, `lib.rs:1120-1122,1150`), not only for the ones that keep
the transport. On the audio thread, `Executor::process`
(`crates/mooloop-engine/src/executor.rs:220-255`) moves `prepared.render` out
with `mem::replace` (`:244`) and pushes it down the reclaim ring, then reads
`prepared.carry` (`:243`) and `prepared.generation` (`:253`), and the loop
body ends. `prepared` still owns `carry`. Four `free()` calls run in the
callback, one per non-empty vector, on every channel or track add, remove,
move, paste and undo, and on every document open.

The contract this breaks is the project's own: `CarryPlan`'s doc says
"allocated here off-thread" (`lib.rs:434`), `carry_strips_from` says "above
all no allocation" (`executor.rs:623-627`), and `StructuralReclaim::RenderState`
exists precisely so that "the box is destroyed when `EngineHandle::poll`
drains this variant" (`lib.rs:353-356`). The allocation test written for the
feature, `carrying_strips_allocates_nothing` (`executor.rs:631-664`), wraps
`COUNTING` around the bare `carry_strips_from` call (`:648-650`), not around
`Executor::process` with an `InstallProject` in the queue, so the frees
happen outside the window it measures. It is the one-sided guard AGENTS.md
describes: green, correct about what it reads, and not reading the copy that
fails.

Cost today is four small frees per edit, which on glibc is an arena lock
each. It is not a crash. It is the class the last two weeks removed from the
sampler, the reclaim vector and MLP8's chorus, reintroduced by the feature
built to make edits cheap, in the block that feature runs in. Plan A.

### 2. Two `ArcSwap` guards on the audio thread can be the last owner of the value the control thread just replaced — LOW today, higher the day recording reads a third

`RenderState::apply_midi` holds `self.buffer_midi.load()` for the whole
message loop (`crates/mooloop-engine/src/render.rs:4969-4971`; the shadowing
`let map = map.as_deref().copied()` does not end the guard's scope), and
`play_note` holds `self.midi_routing.load()` across its channel scan
(`render.rs:5078-5100`). The writers are `SharedCells::set_midi_routing`
(`crates/mooloop-engine/src/lib.rs:613-616`) and `set_buffer_midi_map`
(`lib.rs:1273-1275`): each does `store(Arc::new(..))` and keeps no other
reference to the value it replaces.

arc-swap's hybrid strategy settles a live guard at `store` by handing it a
full `Arc`; the writer then drops its own. When the store lands while the
callback is inside `play_note`, the guard's drop is the last reference and
`MidiRouting { routes: Vec<..> }` (`render.rs:3002`) is freed on the audio
thread, two frees. The window is one note-on's channel scan against a picker
change or a port hot-plug, so the odds are low and the object is small. The
comment at `lib.rs:1272`, "built and dropped on this thread; the audio thread
only loads it", is the belief that is not quite true.

This is the same mechanism `reports/fable-2026-09-17.md` finding 2 found on
`ChannelAudioSlot` (also an `ArcSwapOption`, `render.rs:105`), fixed by
`load_full` plus retirement through the reclaim ring. Two of the three
`ArcSwap`s in `RenderState` (`render.rs:2995-3009`) still use the guard.
The third, `audio_input_routing`, is read by nothing yet
(`render.rs:4906-4912`) and `audio-recording/03` will read it every block,
which turns a note-on-sized window into a permanent one. Plan B.

### 4. The source device's header title is a third copy of the kind-label list, and the only one no test reads — MEDIUM

Commit `3fff067` unified the toolbar picker and the rack's `+` menu on
`SourceKinds.labels` (`crates/mooloop-ui/ui/channel-rack.slint:61-65`) and
wrote `tests/source_kind_menu.rs`, which reads both `.slint` files and holds
the list against `DeviceKind::label()` and `device_kind_to_int`
(`crates/mooloop-ui/src/lib.rs:2216-2247`). The same commit left the
`DeviceHeader` in the device rack spelling its own eight strings as a ternary
ladder on `root.source-kind` (`crates/mooloop-ui/ui/main.slint:4485-4491`).
`source_kind_menu.rs` never looks at it; nothing does. Adding a ninth source
kind (the layer device `plans/README.md` says is wanted, or a plugin
instrument) extends two guarded lists and a compile-time match, and the
header keeps saying "Aux In" for every kind past the seventh.

Fix is one line: `name: SourceKinds.labels[root.source-kind]`, and the
existing test covers it once it asserts the header reads the global. The
comment on `add-channel-clicked` (`main.slint:1036`, "0=Sampler, 1=Drum,
2=Mono, 3=Poly") lists four of the eight values the callback has sent since
the same commit; fix it in passing. Plan C.

### 5. The DSP clamps still spell the ranges the descriptors now own — LOW

`eadd445` (yesterday's Plan A) gave the oscillator range one home,
`OSC_SEMITONE_RANGE`/`OSC_CENT_RANGE` (`crates/mooloop-core/src/generator.rs:402-406`),
and a face test that reads it. The per-voice tuning code still clamps to
literals: `crates/mooloop-dsp/src/mlm1.rs:442` and `polysynth.rs:404`
(`.clamp(-48.0, 48.0)`, `.clamp(-100.0, 100.0)`), and the drum tune
descriptor's `-48..48` (`generator.rs:207-208`) is repeated at
`drumsynth.rs:251`, `sampler.rs:85` and `crates/mooloop-ui/src/lib.rs:11179`.
`dupe-audit repeated-line` reports the `mlm1`/`polysynth` line
(three files). Widen a descriptor and the knob travels where the voice
will not follow; nothing reads the pair. Two hours, and it belongs in the
same worktree as the unchecked-face widening Plan A of yesterday asked for.
