# Whole-system review, 2026-09-17

Scope: seams (two owners, duplicate abstractions, UI/engine drift), real-time
safety of the audio callback, and architecture fit for automation, recording,
plugin hosting and instrument tracks. Read against `main` at `1009be4`.

Method: four parallel investigators briefed with `docs/LOOSE_ENDS.md`,
`SCOPE.md` §5/§8, `FOCUS.md` and `plans/archive/control-plane-seams/`; every
kept finding re-read at the cited lines by the author, and the top three
handed to a fresh-context refuter. Items already recorded in those documents
are omitted. Severity is what a user hears or loses, not how wrong the code
looks. Nothing in the source was changed.

## Findings, ranked by impact

### 1. The Reverb face opens with every knob at zero, and one knob it can never show — HIGH, live since 2026-09-16

`EffectSlotRow.pN` is filled **by descriptor id** since `3b7ba12`
(`crates/mooloop-ui/src/lib.rs:1793` states the rule; the loop is
`lib.rs:2030-2039`, `p[descriptor.id]`). Reverb's ids are 8..15, because
0..7 are retired convolution-era ids (`crates/mooloop-core/src/effect.rs:1876-1890`).
The Reverb face still reads `slot.p0`..`slot.p7`
(`crates/mooloop-ui/ui/main.slint:5026-5033`), which nothing fills for this
kind. Three consequences:

- Every Reverb knob opens at 0, whatever the saved values: `p0..p7` keep
  the array's zero initialiser (`lib.rs:2015`). The write side is right — a
  knob turn goes `effect-param-changed(index, position, v)` →
  `Session::set_effect_param` → `descriptors[position].id`
  (`crates/mooloop-session/src/effects.rs:604-606`) — so the sound follows
  the knob the user just moved while the display it opened with was a lie.
  The knobs are two-way bound (`reverb-device.slint:173`, `value <=> root.size`),
  so what happens after the first touch depends on Slint's binding
  semantics and was not run; "opens at zero" is the verified claim.
- Low Cut (id 15) is never carried at all: `EFFECT_ROW_DESCRIPTOR_PARAMS` is
  15 (`lib.rs:1793`), the loop `continue`s past it (`lib.rs:2032-2034`), and
  `p15` is the slot reserved for the delay's tempo-sync flag.
- The `debug_assert!` at `lib.rs:2041-2047` — every descriptor id must be
  below 15 — is false for Reverb. A dev-profile `cargo run` panics the
  moment a Reverb slot is drawn. CI is green because no test builds a Reverb
  row through `effect_slot_row`; `source_snapshot.rs:686` constructs its row
  by hand and sets `p1` directly.

Why it got through: the commit that changed the scheme rewrote its doc
comment to say "by id and not by position, which used to be the same
statement" and audited the Buffer face, which was the face in hand. The one
test at the id/position boundary, `the_buffer_face_sends_descriptor_positions_for_edits`
(`crates/mooloop-ui/tests/slint_face_agreement.rs:62`), checks the *write*
side for Buffer only. No test reads any face's `pN` bindings, and every
other kind has `id == position` so the change was invisible there. Reverb
is the only table whose ids do not start at 0 — the same shape as the Buffer
incident `AGENTS.md` records, one day later, from the fix.

Fix S: bind the face to `p8`..`p15`, grow `EFFECT_ROW_PARAMS` so id 15 has a
non-reserved slot, and add the read-side twin of the Buffer test — parse each
`if slot.kind == N` block in `main.slint`, map `property: slot.pK` back to the
descriptor the face's `modulation-allowed[K]` names, and assert `K == id`.
Plan 1 below.

### 2. `Sampler::trigger` can free a sample buffer on the audio thread — MEDIUM

`crates/mooloop-dsp/src/sampler.rs:726` assigns `voice.sample = Some(sample.clone())`
on every note-on, dropping whatever `Arc<SampleData>` the voice held from its
last note. `Voice::reset` (`sampler.rs:329-332`) and `Sampler::reset`
(`sampler.rs:627-629`) both go out of their way *not* to do this, with
comments naming the hazard, and the browser preview voice got a bounded
retirement ring for the same reason (`control-plane-seams/04`). The ordinary
voice-steal path never got the same treatment.

When the drop is the last reference: the channel's bank is replaced on the
control thread (`crates/mooloop-engine/src/lib.rs`, `set_channel_audio` →
`ArcSwapOption::store`), the session's `ChannelState.sample_data` is
overwritten in `apply_loaded_sample` (`crates/mooloop-ui/src/lib.rs:14310`),
and that function records no undo entry. So loading sample B over sample A
and then playing a note leaves each voice that last played A as A's only
holder; the next reuse of that voice frees A's frame buffer inside
`trigger()`. Undo history pins a sample only if an undoable edit was recorded
while it was loaded (`ProjectSnapshot.samples`,
`crates/mooloop-session/src/project.rs:16`), which the load-play-load-play
auditioning loop does not do. A second, narrower window: the
`Arc<ChannelAudioSnapshot>` from `load_full()` at `sampler.rs:672` is dropped
at the end of `trigger`, and is the last holder if a store landed in between.

What a user hears: nothing for a short one-shot; a click or xrun when the
freed buffer is a long file, at small JACK periods. Not measured by any test
— `a_block_that_retires_a_preview_does_not_allocate` covers one block and
one path, and the counting allocator counts allocations, not frees.

Fix M: a per-sampler fixed ring of displaced `Arc<SampleData>` drained into
the existing reclaim path, sized `MAX_SAMPLER_VOICES`; and an allocation-and-
free test that swaps the bank and re-triggers. Plan 2.

### 3. `RenderState::reclaim` is an unbounded `Vec` the audio thread pushes to and never drains — LOW today, MEDIUM the day channel removal goes incremental

The field is `Vec::new()` (`crates/mooloop-engine/src/render.rs:2989`);
`EffectChain::clear` pushes to it (`render.rs:1017`). Two callers run on the
audio thread: `StructuralCommand::AddChannel` reusing a populated spare slot
(`render.rs:3908`) and `EngineCommand::RemoveChannel` (`render.rs:4099`). The
structural path checks the *ring's* capacity (`executor.rs:163-166`) but
this vector is not the ring; nothing forwards its contents into the
`StructuralReclaim` the executor pushes, so a displaced node both allocates
on push and is stranded in the live generation for its lifetime.

Reachability today: none. `EngineCommand::RemoveChannel` has no sender
outside a unit test (`crates/mooloop-core/src/bridge.rs:86` defines it;
channel removal rebuilds the whole `RenderState` via `install_project`), and
`set_active_channels` is only ever lowered from that arm (`render.rs:4101`),
so in production a spare slot is always empty when `AddChannel` reuses it
and the push is a no-op. It fires the day anyone wires incremental channel
removal — which `LOOSE_ENDS.md` "Every structural edit stops the song" is
asking for — and it fires as an allocation plus a leak on the first
removal, not under load.

Fix S: pre-size the vector at `RenderState::new`, and have `apply_structural`
move its contents into the returned `StructuralReclaim` (`ReclaimedEffect`
already exists). Plan 3.

### 4. A knob edit under a playing automation lane emits one stray value — LOW

`set_effect_param` (`render.rs:3749-3761`) writes the base and queues an
immediate `ParamValue` unless `effect_is_modulated` (`render.rs:3730`) says
a route will overwrite it. It does not ask whether a *lane* will.
`control_events_for_slot` (`render.rs:1202`, base at `render.rs:1263-1267`)
then replaces the base with the lane's value at every control tick, so the
knob's value sounds for at most 32 frames. Inaudible on most parameters; a
click on a delay time or a stepped mode.

The larger point is that precedence between manual, automation and
modulation is positional — one `unwrap_or` and one boolean — not a stated
rule. Recording automation adds a fourth writer (the recorder must know
whether the knob or the lane is the current value) and a hosted plugin's
own GUI a fifth. Plan 4 makes the rule explicit before those arrive.

### 5. dB↔linear exists twice with floors 120 dB apart — LOW

`crates/mooloop-dsp/src/dynamics.rs:17-30` floors at 1e-9 (about -180 dB)
and never returns 0; `crates/mooloop-core/src/gain.rs:28-89` floors at
-60 dB and returns exact 0 below it. `crates/mooloop-dsp/src/strip.rs:350-356`
records that the difference already bit once and defends the current state
with a range argument ("Makeup's range is 0..24 dB") that no test holds.
The three call sites of the dsp pair are `effects/dynamics.rs`, `strip.rs`
and `engine/meters.rs`. Plan 5.

### 6. The Core Audio callback takes a `try_lock` every block — LOW, macOS only

`crates/mooloop-engine/src/coreaudio_driver.rs:677`. Non-blocking, and
contention is designed out (the old stream is stopped before the new one
starts), so this is against the letter of `AUDIO_ARCHITECTURE.md`'s "no
locks" and not against its intent. Recorded because the locks half of the
RT contract is measured by nothing, and this is the one call a future
detector would have to special-case.

### Seams that were looked for and not found

- Session mirrors and reconcilers (`mooloop-session/src/engine.rs`): the
  control-plane-seams work of 2026-09-15 holds; delivery is `#[must_use]`
  and mirrors advance only on a delivered send.
- `WAVEFORM_BINS` is declared in both `session.rs:329` and
  `buffer_device.rs:50`, both 256, for two unrelated features. Coincidence,
  not one fact written twice; a rename would stop the next reader wondering.
- The JACK callback, the executor, MIDI decode, the sequencer, transport,
  meters, every `process`/`skip_block` in `mooloop-dsp`, and the reverb
  `resize()` path: no allocation, lock or I/O found. Offline export runs the
  same `process_once_block` as the callback (`offline.rs:185,194`).

## Architecture: what will fight the next four features

Each item states the fact in the tree, then whether it is cheaper now.
Items `SCOPE.md` §5 already lists for CLAP (static descriptor tables, the
closed `EffectParams` enum, static latency, no boxed source slot, no
control-thread handle, hard-coded menus) are not repeated.

**Tempo is one scalar, and musical position is an accumulator.**
`Transport { bpm: f64 }` (`crates/mooloop-engine/src/transport.rs:66-71`),
`ticks_per_sample` from that one value (`transport.rs:87-89`);
`position_ticks` accumulates rather than deriving from `frames_played`
(known, `LOOSE_ENDS.md`). Tempo automation, a tempo ramp during recording,
or a plugin asking for host time at a future tick all need a map compiled
into block segments — `AUDIO_ARCHITECTURE.md` "Time" already asks for it.
Cheaper now: `frames_played` is documented as the anchor and nothing else
reads `bpm` as anything but a field. Every device that grows a tempo-synced
parameter from here widens the change.

**Automation is clip-scoped; there is no song-level lane.** Lanes live on
`ChannelPattern.lanes` (`crates/mooloop-core/src/pattern.rs:92`), addressed
by `ParamAddr`, capacity 8 lanes × 1024 points. Song mode replays the same
lane at every placement of its pattern (`sequencer.rs:484-520`). A part
that automates across bars, or recorded automation over an arrangement, has
no home; adding it later means a second resolution path beside
`automation_lane_at` and every caller of `has_automation_at` checking both.
Cheaper now: decide the address space (per-placement lanes vs. an
arrangement lane) before recording is built to write into one of them.

**A note store is a fixed pattern, and the playlist places whole patterns.**
`MAX_PATTERN_STEPS = 256` (16 bars), `MAX_NOTES_PER_CHANNEL_PATTERN = 1024`
(`pattern.rs:13,27`), preallocated so the audio thread never grows them;
`PatternPlacement { pattern, start_tick }` places every channel's pattern at
once on one global timeline (`crates/mooloop-core/src/playlist.rs:38-51`,
`MAX_PLAYLIST_BARS = 64`). An instrument track — one channel, a four-minute
part, two thousand notes — hits both ceilings and has no per-channel clip to
live in. This is the real fork: groovebox-with-song-mode versus per-track
clips. It is not a constant bump, and every feature built on the shared
timeline (pattern-phase swing, `set_pattern_length`, clip automation) makes
the fork wider. Name it before step 10 of `plugin-hosting/` (CLAP
instruments) builds against the pattern-note ceiling.

**A channel is a position, not an identity.** `Channel` has no id
(`crates/mooloop-core/src/channel.rs:119-151`); reorder is a permutation run
through `rescope_after` (`crates/mooloop-session/src/session.rs:800`,
`crates/mooloop-core/src/project.rs:1268`), and the sample-request token of
`control-plane-seams/05` had to be index-keyed for the same reason. Devices
inside a channel do have `DeviceId`. A hosted plugin instance, a recording
take, a spectrum subscription (known), and any engine-side handle will all
want to name a channel across an insert or a removal. Cheaper now than after
plugin instances and takes are keyed by index in three more crates.

**Recording has MIDI capture and nothing else.** `capture_note_on`
(`render.rs:4731`) timestamps into pattern ticks under record-arm; there is
no overdub or merge rule. Audio: JACK registers two outputs and one MIDI in
(`crates/mooloop-engine/src/jack_driver.rs:205-213`), the Core Audio driver
opens no input, only three `rtrb` rings exist and all carry control data, and
offline export drives `process_once_block` synchronously on the caller's
thread (`offline.rs:176-189`) rather than tapping the live callback. The
Buffer device is a real always-recording ring (`buffer_device.rs`) but it is
scoped to its slot in a chain, not to a channel or an input. Two decisions are
cheaper now: whether "record this channel" is a channel-level tap (the
`AudioTaps` machinery Aux In reads is reusable) or Buffer-at-slot-0, and that
the driver gains an input port before a third driver is written without one.

**Plugin hosting: three things are easier than the plan assumes, one harder.**
Easier: `ProcessContext` already carries `bpm`, `position_ticks` and
`position_frames` (`crates/mooloop-dsp/src/node.rs:49-52`), so host time
info is free; `StructuralCommand::InstallEffect`/`ReplaceEffect` already move
a `Box<dyn AudioNode + Send>` over the ring with reclaim-not-drop
(`crates/mooloop-engine/src/lib.rs:189,208`), so the boxed *source* slot is a
copy of an existing path; the 8 ms pump body holds no blocking call, so a
CLAP main-thread callback can run inside a tick. Harder: `format_version` is
an exact-match gate with one bespoke fixup (`crates/mooloop-project/src/lib.rs:982,1118`),
so the first plugin state blob forces the first real migration story, and
adding one device kind touches roughly 25-30 exhaustive matches across six
crates (`device-registry/00-status.md` counted them and parked the registry).

**Precedence between writers is implicit.** See finding 4. One function
composes knob, lane and route; recording and plugin GUIs are two more
writers. A stated rule (and a test per pair) is a day's work now.

## Plans

Each is sized for a Sonnet-class model working alone in a task worktree, with
the verification rung it needs. Order is by value, not dependency; none
depends on another.

## Outcome, same day

**All five plans landed on `main` on 2026-09-17** and were pushed, each with
a test that failed on the unfixed tree first, followed by a full workspace
test and `clippy -D warnings` run on the combined tree. What the work found
that this report did not:

- **Plan 1:** there were ten wrong reads, not nine. The Delay and Modulation
  faces also read their tempo-sync flag from `p15`, the same field Reverb's
  Low Cut needs.
- **Plan 2:** the sampler also has to retire the channel snapshot it holds,
  not only voice samples. Otherwise holding the snapshot turns a rare race
  into a free on every load.
- **Plan 3:** the last two allocations in the reused-slot block came from
  `MlP8::reset`, whose chorus rebuilt its delay line on the audio thread.
  That was reachable through `SetChannelSource`, and it now resets in place.
- **Plan 4:** finding 4 overstated the glitch. The stale knob value was
  overwritten within the same frame rather than sounding for 32 frames, so it
  only mattered to devices that act on every value they receive.
- **Plan 5:** `dupe-audit twin-names` went from six leads to seven, not down
  by one. The cross-crate pair is gone, but the check pairs any function with
  its inverse, and both conversion pairs now live in `gain.rs`.

**The architecture section, as Adam answered it:**

- **Patterns stay, and there are no per-track clips.** Song-level automation
  does not exist: clone a pattern and split the ramp. See `PRODUCT.md`
  "Working Decisions".
- **Audio recording goes into the sampler through one input menu.** Planned in
  `plans/audio-recording/`.
- **A channel gets a durable id.** Planned in `plans/archive/channel-identity/`.
  Surveying it found blocker 7 of `plugin-hosting/`: a channel edit would
  reload every plugin.
- **The tempo item needs no action.** Tempo maps are out of scope for 0.2, and
  `LOOSE_ENDS.md` deliberately defers the position running-total fix until a
  tempo map exists.
- **The format-migration item needs no action for plugins.** Their state is
  opaque bytes that each plugin versions itself, and `plugin-hosting/` keeps
  the format at version 1 with defaulted fields.

The recording survey also turned up two bugs in the shipped MIDI path:
per-channel routing was dropped on every project install, and notes recorded
after the first pattern pass landed on the last tick. Both are being fixed on
`fix/midi-routing-and-record-wrap`.
