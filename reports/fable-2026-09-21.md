### B. Arming record dirties the document, against the rule written two lines above the call — LOW/MEDIUM

"Not an edit" is spelled in two places and they disagree. The UI's
`on_record_armed_toggled` (`crates/mooloop-ui/src/lib.rs:9262-9278`) says in
its comment that arming "must not make an untouched document look unsaved --
the same rule the transport commands already follow", and sends the
`SetRecordArmed` that `Session::set_record_armed` returns
(`crates/mooloop-session/src/midi.rs:542-548`) down the ordinary command
path. The rule itself lives in `Session::apply_engine_message`
(`crates/mooloop-session/src/engine.rs:691-694`), where `edits` is
`!matches!(command, Play | Pause | Stop)` -- three variants, and
`SetRecordArmed` is not one of them -- so `edits && self.became_dirty()`
(`:701`) marks the session dirty on every arm and disarm. The title takes
its `*` and quit asks about a document nothing changed. A control surface's
transport arm (`midi.rs:1100`) goes the same way. The list at `engine.rs:693`
is the only copy of the policy the code reads; the comment at `lib.rs:9262`
is a copy nothing reads. The test at `engine.rs:882` covers what an install
discards, not what dirties. Plan B.

### C. A refused one-shot command is reported once per process, then never — LOW

`Session::report_refused_command` (`crates/mooloop-session/src/engine.rs:788-800`)
latches `engine_queue_refused` (`session.rs:192`, set at `:792`, cleared
nowhere: three references in the crate) and returns early after the first
refusal. The message it logs is correct -- a one-shot edit "has diverged from
the visible project" -- and is delivered exactly once in the life of the
process, so a second full ring, on a later song, diverges silently. The
window and session copies are written before the send in every caller
(`lib.rs:9270-9276` is one; the pattern is general) and nothing rolls them
back, which the comment at `engine.rs:695-697` already says. Cheapest
honest fix: reset the latch when the queue drains (`EngineHandle::poll`
reports it) or key it per document in `replace_project`; either is one line
and a test. Folded into Plan B.

### E. ML-P8 carries a delay line the seek hook cannot reach — LOW/MEDIUM, audible

Step 03 gave `AudioNode::on_discontinuity` to delay, modulation, reverb and
plate, and `RenderState::on_discontinuity`
(`crates/mooloop-engine/src/render.rs:4536-4543`) fans it out to every live
strip's source and chain and every bus chain; `ChannelStrip` forwards it to
`source_node_mut()` (`:2580-2583`). The eight sources all take the trait's
default (`crates/mooloop-dsp/src/node.rs:337`; no `fn on_discontinuity` in
any of `sampler.rs`, `drumsynth.rs`, `monosynth.rs`, `polysynth.rs`,
`mlm1.rs`, `mlp8.rs`, `ds01.rs`), which is right for seven of them: their
time-state is voices, and a seek still chokes voices. The eighth, ML-P8,
holds a `Chorus` (`mlp8.rs:1675`) that is "one shared `ModulationEffect`"
(`:921-928`) -- the same type that opted in at
`effects/modulation.rs:298` to empty its line on a seek -- and nothing calls
`self.chorus.effect.on_discontinuity`. A chorused ML-P8 keeps its line
running between notes on purpose (`node.rs:513`,
`a_chorused_mlp8_declines_to_rest_between_notes`), so what was in the line
before a seek or a loop fold rings across it, which is exactly the artifact
step 03 removed for the standalone effect. One three-line override and one
test. Plan C.

Two neighbours checked and left alone. `FilterEffect` (`effects/filter.rs:155-167`)
says of itself that its settling time "runs from a few samples ... to
effectively forever as it approaches self-oscillation", and takes the default
hook, so a self-oscillating filter plays through a seek with continuous
phase; under the modulation rule ("free-running state has to arrive at the
same phase whether or not the transport moved") that is arguably correct,
and it is a question for Adam rather than a defect. The console strip
(`strip.rs`) is not an `AudioNode` and is outside the fan-out, which
`docs/AUDIO_ARCHITECTURE.md:254-255` already says.

### G. Opening an automation lane mallocs on the audio thread, and three paths free one there — MEDIUM/HIGH

`crates/mooloop-core/src/automation.rs:9-10` says "lane edits are applied on
the audio thread and must not allocate", and `pattern.rs:165-167` says
`open_lane` "never reallocates on the audio thread". Both are true of the
outer `lanes` vector (`ChannelPattern::new`, `pattern.rs:103`, reserved to
`MAX_AUTOMATION_LANES_PER_CHANNEL`) and false of what it holds:
`open_lane` (`pattern.rs:168-177`) pushes `AutomationLane::new(target)`,
whose body is `Vec::with_capacity(MAX_AUTOMATION_POINTS_PER_LANE)`
(`automation.rs:68-74`; 1024 points, 12 KB). The chain from the callback is
`Executor::process_with_input` → `apply_command` →
`EngineCommand::OpenAutomationLane` (`render.rs:4876-4883`) →
`Sequencer::open_automation_lane` (`sequencer.rs:270-280`) → `open_lane`;
`UpsertAutomationPoint` (`render.rs:4908`, `sequencer.rs:310-320`) opens
the lane the same way, so the first breakpoint drawn on a destination
allocates too. The session sends both live
(`crates/mooloop-session/src/automation.rs:66,159,188`).

The frees are the same object from the other end. `RemoveAutomationLane`
(`render.rs:4884-4895` → `sequencer.rs:281-291` → `pattern.rs:179-182`,
`lanes.remove(index)`, dropped at the `.is_some()`);
`StructuralCommand::RemoveEffect` → `forget_device` (`render.rs:3894`) →
`structure.rs:759` `lanes.retain(..)`, which the comment at
`pattern.rs:184-186` calls "without allocating" and which frees instead;
and `StructuralCommand::AddChannel` (`render.rs:4369`) →
`Sequencer::clear_channel` (`sequencer.rs:171-178`), which walks
`&mut self.patterns` -- the whole preallocated bank, `MAX_PATTERNS = 256`
(`channel.rs:13`), not `active_patterns` as `forget_device` beside it is
bounded (`sequencer.rs:344-346`) -- and `lanes.clear()`s each. Up to
256 × 8 frees on Add Channel, and 256 iterations of nothing in the usual
case. `ClearAutomationLane` (`automation.rs:170-172`, `points.clear()`)
keeps its capacity and is clean, which shows the intent.

No allocation-counting test measures any of these: the three in
`executor.rs` (`:691`, `:713`, `:799`) cover install, the carry plan and the
routing tables. `reserve_points` (`automation.rs:106-112`) exists for the
decode path, so the inner vector's capacity was thought about, on the one
path that runs off the thread. Plan A.

### H. A loop fold now zeroes every delay, reverb and plate ring in the project, every lap — MEDIUM, and a question

`render.rs:5683-5695` sets `jumped` from `span.jumped`, which
`transport.rs:154-155` reserves for a loop fold; `:5708-5710` then sends
`on_discontinuity(Discontinuity::Seek)` to every live strip's source and
chain and every bus chain (`:4536-4543`, `:1571-1577` including bypassed
and sleeping slots). Delay (`effects/delay.rs:221-229` →
`delayline.rs:56-60`, `fill(0.0)` on a two-second stereo ring: 768 KB at
48 kHz), reverb (`reverb.rs:603-615`, eight lines, four diffusers, a
predelay) and plate (`plate.rs:395`) all clear on `Seek`. That landed in
`6e76c56`, after yesterday's tree, and is deliberate: the plan says the hook
is "said by the engine at a seek, a loop fold, a stop". Two things it did
not weigh.

The cost scales with the project and not the block: a fold is every few
seconds in a loop-based instrument, and each one is a memset of every
tail-holding ring in the song inside one callback, on top of the voice
release that was already there (`:5687`). Nothing measures it;
`block_cost.rs` has no fold case.

And the behaviour is the one a groove box is least expected to have. Voices
were already released at the fold, so the delay's *input* stops; clearing
the *line* means no repeat and no reverb tail ever crosses the loop point,
which is audible on every lap of every song with a delay in it. Whether a
fold is a seek for a tail is Adam's call, and `Discontinuity` has no variant
that lets a node tell them apart (`node.rs:150-164`: `Seek`, `Stop`,
`ProgramChange`), so today the delay cannot decline the fold without also
declining the seek. Plan C makes it expressible; the default stays his.

### I. Three bounded costs on the callback that grow with the song, not the block — LOW/MEDIUM

- **Song-mode automation lookup.** Once `has_automation_at`
  (`sequencer.rs:477-501`) is true, `curve_for` (`render.rs:780-794`) is
  asked once per source descriptor per channel (`:5903-5905`), per internal
  route (`:5956`), per effect descriptor per slot (`:1360`) and twice per
  strip (`:2024`), and each call is `automation_lane_at` (`sequencer.rs:526-574`),
  which in Song mode walks the whole playlist (`:545`, up to
  `MAX_PLAYLIST_PLACEMENTS = 512`) and, per covering placement,
  `active_channels × 8` lanes. It is zero until the first lane exists under
  the playhead and then order playlist × channels × destinations per
  block. A per-block cache of "covering placements" would make it
  O(destinations).
- **`EventList::push_ordered`** (`event.rs:122-133`) is an insertion sort
  into `MAX_EVENTS = 256` (`:74`) whose headroom comment reasons about
  notes; automation and modulation emit one event per control tick per
  destination (`render.rs:5930-5936`, `CONTROL_RATE_FRAMES = 32`), so at an
  8192-frame block (`bus.rs:15`) one automated destination fills the list
  alone and every later push returns `false` into a `let _`. Silent, no
  allocation, wrong values.
- **`Sequencer::set_playlist_placement`** (`sequencer.rs:123-144`) does
  `push` then `sort_unstable` (`:134-135`) on the callback per placement
  toggle, and painting a range sends one per cell. Capacity is reserved
  (`:70`), so it is time and not memory; an insert at `partition_point` is
  the same line count.

Also on the thread and noted, not ranked: `defer_command`'s
`debug_assert!(false, "... {command:?}")` (`render.rs:4591`) formats an
`EngineCommand` and panics from the callback in a dev-profile run when all
eight slots are held, and drops the command silently in release with no
counter; there is no caller yet. And the Core Audio `try_lock`
(`coreaudio_driver.rs:970`) is unchanged since 09-17 finding 6; the new
input stream added no second lock.
